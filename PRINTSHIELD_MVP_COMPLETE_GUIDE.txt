PRINTSHIELD MVP - COMPLETE PROJECT GUIDE
==========================================

1. PROJECT OVERVIEW
-------------------
PrintShield is a privacy-first secure-printing application concept built for a hackathon.

The problem:
People commonly send highly sensitive files to a photocopy or print shop through WhatsApp,
email, Telegram, or similar tools. This creates a loss-of-control problem. The original file can
be retained, forwarded, copied, or accessed after the user intended it to be printed.

Examples of sensitive documents include:
- Aadhaar cards
- PAN cards
- Passports
- Bank statements
- Income or caste certificates
- Medical reports
- School and university certificates
- Legal documents
- Employment records

The PrintShield vision is to let a user create a temporary, user-controlled print job instead of
sending the full document permanently through an ordinary messaging application.

The current repository is an Android-first Flutter MVP. It prioritizes a polished, demonstrable
user experience over production infrastructure.

3. WHAT IS NOT IMPLEMENTED YET
------------------------------
The app does NOT currently encrypt documents.
The app does NOT currently pick a real document from device storage.
The app does NOT transmit a document to a shop.
The app does NOT connect to a printer.
The app does NOT scan QR codes; it generates the customer-side pairing QR.
The app does NOT authenticate a print-shop client.
The app does NOT create real temporary permissions on a server.
The app does NOT revoke a received file from another device.
The app does NOT perform AI or OCR-based sensitive-data analysis.
The app does NOT use Ethereum or submit blockchain transactions.
The app does NOT provide a cryptographic proof of a print job.

These limits must be communicated accurately during a hackathon demo. The product demonstrates
the UX and architecture for secure print jobs; it does not falsely claim that a document is
currently protected by encryption or blockchain.


4. TECHNOLOGY STACK
-------------------
Primary framework: Flutter
Language: Dart
Primary platform: Android
Material system: Material 3
External package: qr_flutter ^4.1.0

Why Flutter:
- Fast iteration speed for a hackathon.
- One codebase for Android first, with iOS/web/desktop potential.
- Strong animation, layout, routing, and Material component support.
- Easy future integration with native Android printing APIs and camera/QR plugins.

Why qr_flutter:
- It generates an actual scannable QR code.
- It is a small, justified dependency for the pairing experience.
- It avoids pretending that a decorative image is a QR workflow.

No package was added for encryption, file selection, blockchain, printing, or AI because those
features are not implemented in a misleading/demo-only way yet.

11. ADAPTIVE DEMO PRIVACY SCORE
-------------------------------
File: lib/core/state/print_job_draft.dart

PrintJobDraft extends ChangeNotifier.

Stored fields:
- copies
- expiryMinutes

Default fields:
- 1 copy
- 15 minutes

Adaptive behavior:
- A 5-minute expiry receives a higher demo score.
- A 15-minute expiry receives a middle-high demo score.
- A 30-minute expiry receives a lower demo score.
- Each extra copy reduces the score.

Current scoring heuristic:
- 5 minutes starts at 96.
- 15 minutes starts at 90.
- 30 minutes starts at 80.
- Each additional copy subtracts 4 points.

This score is explicitly a UI heuristic. It is NOT:
- A cryptographic confidence score.
- A security audit result.
- A measure of actual encryption strength.
- A claim that the document cannot be copied.

The score explanation exposes its exact inputs, for example:
"Based on 1 copy and a 15-minute expiry."

This transparency is important for a privacy product.

15. QR PAIRING SCREEN
---------------------
File: lib/features/pairing/presentation/qr_pairing_screen.dart
Class: QrPairingScreen

This is a StatefulWidget because it manages a temporary-expiry countdown timer.

What the screen does:
1. Reads the selected expiry length from PrintJobDraft.
2. Starts a one-second periodic Timer.
3. Generates a QR code using QrImageView from qr_flutter.
4. Displays a mm:ss countdown.
5. Fades the QR visual when it expires.
6. Allows generation of a new code after expiry.
7. Provides a simulated pairing confirmation button for the demo.

The current QR payload format is similar to:
printshield://pair?job=PS-DEMO-4821&expires=<seconds>&mode=demo

Important QR safety boundary:
- The QR contains a demo job reference and expiry count.
- The QR does not contain a document.
- The QR does not contain an encryption key.
- The QR does not grant a real printer access.
- The QR is not proof of a secure exchange.

Future secure QR design:
- Generate a random, server-registered, single-use pairing nonce.
- Include an expiry timestamp rather than a simple countdown number.
- Bind the QR to a job ID and expected print-shop identity.
- Scan with an authenticated print-shop client.
- Require a key agreement or signed challenge-response before delivery.
- Mark the nonce consumed after successful pairing.
- Refuse expired, reused, or untrusted nonces.

23. REAL SECURITY ARCHITECTURE RECOMMENDATION
---------------------------------------------
A production system should use at least two applications/services:

1. Customer mobile app.
2. Print-shop client application.

Optional third component:
3. Minimal backend/relay service for job registration, pairing, and authorization.

Recommended high-level flow:
1. User selects a document locally.
2. User reviews detected/redacted fields.
3. App generates a random per-job content-encryption key.
4. The document is encrypted locally with authenticated encryption.
5. The app creates a single-use short-lived job record.
6. The user scans/pairs with an authenticated shop client.
7. The client identity is verified.
8. The job key is wrapped/encrypted for the paired client or negotiated using authenticated key exchange.
9. The encrypted document is delivered to the approved client.
10. The client decrypts only in controlled temporary storage/memory.
11. The client prints within policy: time, copy count, and one-time usage.
12. The client reports an authenticated completion acknowledgment.
13. The service revokes authorization and deletes temporary materials.
14. The customer sees completion/expiry status.

Important warning:
No mobile app can fully guarantee that a malicious print-shop operator will not photograph the
screen, print an unauthorized copy outside the controlled client, or retain information after
seeing it. PrintShield reduces common digital leakage and introduces auditable controls; it cannot
eliminate all physical-world risk.


24. ENCRYPTION RECOMMENDATIONS
------------------------------
Use established, reviewed cryptographic libraries. Do not create custom cryptography.

Possible design direction:
- AES-GCM or ChaCha20-Poly1305 for document encryption.
- Unique random nonce/IV for every encryption operation.
- Strong random per-job content key.
- Authenticated metadata: job ID, expiry, allowed copies, and client binding.
- Public-key encryption or authenticated ECDH to share/wrap the job key.
- Key material held only as long as necessary.
- Secure platform storage for device-bound secrets.

Never:
- Put encryption keys into a QR code.
- Store raw sensitive documents in app logs.
- Hardcode keys in source code.
- Use a reversible "fake encryption" for a demo.
- Send full documents through an unauthenticated QR payload.


25. AI ANALYSIS RECOMMENDATIONS
-------------------------------
Future sensitive-data detection can use several layers:

- OCR to extract text from scans/images/PDFs.
- Regex or format validation for Aadhaar/PAN/account-like patterns.
- Named entity recognition for names, addresses, dates, and medical entities.
- Computer vision for signatures, faces, QR codes, and document type.
- User review to accept or reject all suggested redactions.

Privacy requirements:
- Prefer on-device processing for sensitive data.
- If cloud AI is used, obtain explicit consent and explain data handling.
- Keep an audit trail of user-selected print/redaction preferences.
- Never silently modify a document without user confirmation.


26. ETHEREUM / BLOCKCHAIN RECOMMENDATIONS
-----------------------------------------
Blockchain should be optional and should never store document contents or personal information.

Potential use case:
- Hash a signed job manifest.
- Commit only the hash, time, and non-sensitive job event to a smart contract or chain.
- Use it as a tamper-evident audit commitment.

Potential proof data:
- Job-manifest hash.
- Timestamp.
- Client public-key fingerprint.
- Completion acknowledgment hash.
- Revocation event hash.

Risks:
- Transaction fees.
- User wallet friction.
- Permanence of public records.
- Complexity that may not help the core printing workflow.

For a hackathon, the best story is "Ethereum-ready commitments" rather than unnecessary live
on-chain document data.
